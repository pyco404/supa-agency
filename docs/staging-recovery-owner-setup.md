`validDurationInSeconds`. Do not copy an old API's singular `bucketId` field.
The existing account's key-administration authority is used only privately by

| Identity | Capabilities | Scope | Proposed lifetime |

| Backup writer | `writeFiles` | One bucket ID; `supa-staging/snapshots/` | 86,400 seconds |
| Recovery reader | `listFiles`, `readFiles` | Same bucket/prefix | 86,400 seconds |

Neither receives delete, key management, bucket management, retention changes,
sharing/download-token generation or governance bypass. Use the Native API for
this minimal proposal; do not grant broad S3-discovery capabilities to make an
unreviewed client work. Generic console Read/Write presets must not substitute
broader permissions. Any genuinely necessary discovery capability needs review.

Important limitation: `writeFiles` includes `b2_hide_file`, so it is **not** a
strictly append-only permission. Uploading another same-name version or hiding a
name is not necessarily denied by Object Lock. Lock protects the retained file
version from deletion. Use unique snapshot UUIDs and pin exact file/version IDs
and signed-manifest hashes in independent inventory. Recover by those identities,
not a mutable latest pointer. The reader must verify older retained versions are
accessible. Verify denied reads for the writer, denied writes for the reader,
out-of-prefix/out-of-bucket denial, anonymous denial and denied deletion/retention
bypass using a separately authorized harmless canary. No such remote tests or
key creation have occurred. [Capability definitions](https://www.backblaze.com/docs/cloud-storage-application-key-capabilities).
